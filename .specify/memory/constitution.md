# tf-gcp-msvc Constitution

## Core Principles

### I. Module-First Design (Bounded Modules)

Every reusable piece of infrastructure MUST be implemented as a standalone Terraform
module before being composed into a stack. Modules are the bounded contexts of this IaC
codebase.

**Module taxonomy:**
- `modules/networks/*` — VPC, subnets, routes, NAT, firewall rules, VPN variants
- `modules/workload/*` — GKE clusters, Artifact Registry, workload-specific resources
- `modules/sql/*` — Cloud SQL engines and read-replica configurations
- *(additional categories added here when new resource families are introduced)*

**Rules:**
- A module MUST have a single, clearly named responsibility (e.g., `vpn-ha` not `networking`).
- Modules MUST NOT reference other modules directly; composition happens only at the
  stack level via explicit variable wiring.
- Every module MUST expose outputs for all values a stack may need; internal resources
  MUST NOT be referenced cross-module.
- Shared constants (regions, CIDR conventions) belong in stack-level `locals {}`, not
  hard-coded inside modules.
- A new module requires justification: if a resource configuration appears only once
  across all stacks, inline it in the stack rather than creating a module.

**Directory contract per module:**
```
modules/<category>/<name>/
├── main.tf        # resource definitions
├── variables.tf   # all inputs
├── outputs.tf     # all outputs
├── versions.tf    # required_providers + version constraints
└── README.md      # auto-generated by terraform-docs (do not hand-edit)
```

**Rationale:** Modular boundaries make resource families independently versionable,
testable in `examples/`, and reusable across environment stacks without copy-paste drift.

### II. Security-First Infrastructure (NON-NEGOTIABLE)

Security and compliance constraints MUST be encoded in Terraform, not applied manually
after provisioning. The infrastructure is the security policy.

**Mandatory requirements:**
- IAM bindings MUST follow least-privilege; no `roles/editor` or `roles/owner` granted
  to service accounts in module defaults.
- All GKE node pools MUST use private nodes; public endpoint exposure requires explicit
  variable override and a documented rationale in the stack.
- Cloud SQL instances MUST use private IP; public IP access is prohibited in modules
  unless explicitly set via variable and flagged in `outputs.tf`.
- Secrets (database passwords, API keys) MUST be sourced from Secret Manager or
  passed as sensitive variables; MUST NOT appear in `.tfvars` files committed to VCS.
- Firewall rules MUST default to deny-all; allow rules MUST be the minimum required
  port/protocol range with explicit description.
- VPN tunnels MUST use IKEv2 and pre-shared keys stored in Secret Manager.
- `*.tfvars` and `*.tfvars.json` files are git-ignored and MUST NOT be committed.
- `tfsec` / `checkov` scan results MUST be reviewed before any `terraform apply` in a
  non-example stack.

**Rationale:** GCP infrastructure mistakes (public IPs, overprivileged service accounts,
open firewall rules) are operational security incidents. Encoding policy in HCL ensures
it is reviewed, versioned, and audited.

### III. State Isolation by Environment

Each environment stack MUST own its own Terraform state. Cross-stack state sharing via
`terraform_remote_state` is prohibited except for read-only network outputs.

**Rules:**
- Each directory under `stacks/` represents one environment (e.g., `dev`, `sit`, `prod`).
- State backends MUST use GCS with a bucket and prefix that identifies the environment
  and stack uniquely (e.g., `gs://<project>-tf-state/stacks/prod/`).
- `stacks/example/` uses local state for development/testing only; it MUST NOT be used
  as a template for production stacks without converting to remote state.
- `terraform plan` output MUST be reviewed and approved before `terraform apply` in any
  non-example stack.
- State lock MUST be enabled (GCS object locks or Terraform Cloud workspace locking).

**Rationale:** Shared state creates implicit coupling between environments. Isolated state
allows independent apply cycles and prevents a failed `dev` apply from blocking `prod`.

### IV. Immutable Infrastructure via Code Review

All infrastructure changes MUST travel through version control and pull request review.
Manual GCP Console changes to managed resources are prohibited.

**Mandatory gates:**
- Every change MUST pass `terraform fmt -check -recursive` (enforced by pre-commit hook).
- Every change MUST pass `tflint` with no errors (enforced by pre-commit hook).
- `terraform-docs` README MUST be regenerated and committed for any module with changed
  variables or outputs (enforced by pre-commit hook).
- Breaking changes to module interfaces (removing variables, changing types) require a
  MAJOR version bump and a migration note in the PR description.
- `terraform plan` output MUST be attached to the PR for any change to a non-example
  stack.

**Rationale:** Manual changes create drift between the codebase and real infrastructure,
making future applies unpredictable and audits unreliable.

### V. Simplicity & YAGNI (Architecture Level)

Infrastructure design MUST use the minimum resource complexity that satisfies the stated
requirement. Speculative provisioning is prohibited.

**Guidelines:**
- Provision the smallest machine type / node count that meets the workload requirement;
  scale-up is a future task, not a default.
- Do not create a new module for a resource used in only one stack—inline it.
- Do not add variable flags for behavior that has not been requested (e.g.,
  `enable_future_feature = false`).
- Prefer GCP-managed services (Cloud SQL, Memorystore, Artifact Registry) over
  self-managed equivalents unless a concrete requirement rules them out.
- Three similar resource blocks across different stacks justify extraction to a module;
  fewer do not.

**Complexity justification required for:**
- Introducing a new resource category (new `modules/<category>/` directory)
- Adding a new GCP API enablement dependency to a module
- Creating generic wrapper modules over GCP provider resources
- Configuring multi-region or cross-project networking

**Rationale:** Infrastructure complexity has a compounding maintenance cost: more resources
mean more drift risk, more state to manage, and longer plan/apply cycles.

### VI. Observable & Self-Documenting Infrastructure

Every module MUST be self-documenting and every stack MUST produce observable, named
outputs that operators can query without reading HCL source.

**Documentation standards:**
- `README.md` in each module is generated exclusively by `terraform-docs`; do not
  manually edit it.
- Variable descriptions MUST be complete sentences explaining purpose, not just type
  repetition (e.g., `"CIDR range for the GKE node subnet"` not `"string"`).
- Output descriptions MUST explain what the value is used for downstream.
- Locals MUST use names that read as infrastructure concepts, not code variables
  (e.g., `gke_private_ip_node_subnet` not `s3`).

**Naming conventions:**
- Resources: `<env>-<component>-<type>` (e.g., `example-main-vpc`, `example-cloud-nat`)
- Modules: noun phrases describing the resource family (e.g., `router-nat`, `vpn-ha`)
- Variables: snake_case with unit suffix where applicable (e.g., `disk_size_gb`,
  `node_count`)

**Observability:**
- Stack outputs MUST expose all values needed by dependent systems (Kubernetes configs,
  CI/CD pipelines) so they can be retrieved via `terraform output` without reading state.
- Label all GCP resources with at minimum: `env`, `managed-by = "terraform"`, `module`.

**Rationale:** Infrastructure that cannot be understood from its outputs alone requires
operators to read source code under pressure. Named outputs and auto-generated docs
reduce incident response time.

## Work Instrumentation

These principles govern **how work is conducted** day-to-day — before, during, and after
implementation. They apply to every Terraform change regardless of size.

### VII. Think Before Coding

All uncertainty MUST be surfaced before writing HCL. Hidden confusion produces
infrastructure that solves the wrong problem — and `terraform destroy` is the fix.

**Before implementing, you MUST:**
- State your assumptions explicitly. If the CIDR range, region, or node count is not
  specified, ask rather than guess.
- If multiple valid designs exist (e.g., shared VPC vs. standalone VPC per environment),
  present both with trade-offs before choosing.
- If a simpler approach exists (inline resource vs. new module), name it and push back
  when warranted.
- If something is unclear, stop. Name what is confusing. Ask.

**Trade-offs MUST be visible:**
- When two valid resource designs exist, state both with their costs before choosing.
- Decisions that affect state structure or module interface are hard to reverse; they
  require explicit acknowledgment before proceeding.

**This principle is satisfied when:**
- Clarifying questions precede the `plan`, not follow the `apply`.
- PRs reflect a single, clear understanding of the requirement.
- No CIDR ranges, regions, or machine types were silently assumed.

**Rationale:** Ambiguity resolved before HCL is free. Ambiguity resolved after `apply`
costs a `destroy` and reprovisioning cycle — potentially with data loss.

### VIII. Simplicity First

Implementation MUST use the minimum resource configuration that satisfies the stated
requirement. Speculative additions are prohibited.

**Hard rules:**
- No resources beyond what was explicitly requested.
- No variables for behavior that has not been asked for.
- No "future-proofing" labels, outputs, or resource blocks.
- No error-handling resources (e.g., alerting policies) for scenarios that haven't been
  specified.
- If a module has 300 lines and the requirement calls for 80, rewrite it.

**The senior engineer test:**
Before submitting any HCL change, ask: "Would a senior infrastructure engineer say this
is over-engineered?" If yes, simplify before proceeding.

**This principle is satisfied when:**
- Every resource in the diff can be traced directly to the stated requirement.
- No new variables were added for a configuration used in only one place.
- Code reviewers do not comment "this is over-engineered."

**Rationale:** Unused resources still appear in `terraform plan`, consume GCP quota, and
add cognitive overhead. Brevity is a feature.

### IX. Surgical Changes

You MUST touch only the HCL required to fulfill the current request. Adjacent modules,
stacks, and outputs are out of scope unless broken by your change.

**When editing existing HCL:**
- Do NOT reformat adjacent blocks you were not asked to touch (let pre-commit hooks
  handle formatting uniformly).
- Do NOT refactor working modules as a side effect of an unrelated change.
- Match existing variable ordering and block style.
- If you notice unrelated issues (unused outputs, wrong descriptions), mention them in
  the PR — do not fix silently.

**When your changes create orphans:**
- REMOVE variable declarations, outputs, and locals that YOUR changes made unused.
- Do NOT remove pre-existing unused items unless explicitly asked.

**The traceability test:**
Every changed line MUST trace directly to the stated requirement. If you cannot explain
why a line changed, revert it.

**This principle is satisfied when:**
- PRs contain no "while I was in here" resource changes.
- Every changed line is explainable against the requirement.
- Unrelated issues are surfaced as PR comments, not silent fixes.

**Rationale:** Unsolicited HCL changes are the leading cause of unexpected plan diffs
and review friction. Surgical PRs are fast to review, easy to roll back, and safe to
apply.

### X. Goal-Driven Execution

Every infrastructure task MUST be transformed into a verifiable goal before HCL is
written. "Make it work" is not a success criterion.

**Before starting, state a brief plan:**
```
1. [Step] → verify: [specific terraform output / gcloud check]
2. [Step] → verify: [specific terraform output / gcloud check]
3. [Step] → verify: [specific terraform output / gcloud check]
```

**Transform vague tasks into testable ones:**
- "Add GKE cluster" → "GKE cluster exists in `us-central1`, private nodes, `terraform
  output gke_endpoint` returns a value"
- "Fix the VPN" → "Tunnel status is ESTABLISHED, `gcloud compute vpn-tunnels describe`
  returns `detailedStatus: Tunnel is up`"
- "Refactor subnet module" → "`terraform plan` shows no changes against current state
  after refactor"

**Loop until verified:**
- Do not declare a task done until the stated success criterion passes.
- `terraform plan` showing no diff is not sufficient — verify the actual GCP resource
  state where applicable.

**This principle is satisfied when:**
- Every completed task has a documented check that was verified.
- No tasks are closed with "should be provisioned" — only "verified by `terraform
  output` / `gcloud describe`."
- Plans are written before HCL, not after.

**Rationale:** Infrastructure is not "done" when `apply` exits 0. It is done when the
resource behaves as specified. Defining done before you start eliminates the loop of
apply → test → fix → apply.

## Technical Standards

### Technology Stack (Locked)

- **IaC Tool**: Terraform 1.3+
- **Provider**: `hashicorp/google` and `hashicorp/google-beta` 5.x – 7.x
- **Cloud**: Google Cloud Platform (GCP)
- **Container Orchestration**: GKE (Autopilot or Standard — specified per stack)
- **Database**: Cloud SQL for PostgreSQL 14+
- **Networking**: VPC, private subnets, Cloud NAT, HA VPN or Classic VPN
- **Registry**: Artifact Registry (Docker format)
- **Linting**: `tflint` with GCP ruleset
- **Formatting**: `terraform fmt` (enforced via pre-commit)
- **Documentation**: `terraform-docs` (enforced via pre-commit)
- **Security Scanning**: `tfsec` / `checkov` (recommended pre-apply gate)

### Repository Layout

```
tf-gcp-msvc/
├── modules/                # Reusable, versioned Terraform modules
│   ├── networks/           # Network resource modules
│   │   ├── vpc/
│   │   ├── subnets/
│   │   ├── routes/
│   │   ├── router-nat/
│   │   ├── firewall-rules/
│   │   ├── vpn-classic/
│   │   └── vpn-ha/
│   ├── workload/           # Compute / container resource modules
│   │   └── artifact-registry/
│   └── sql/                # Database resource modules
│       └── postgresql/
├── stacks/                 # Environment-scoped infrastructure compositions
│   └── <env>/              # e.g., dev, sit, prod, example
│       ├── main.tf
│       ├── providers.tf
│       ├── versions.tf
│       ├── outputs.tf
│       └── *.tf            # One file per logical component (e.g., gke-private.tf)
└── examples/               # Standalone usage examples (local state, for testing only)
    └── ha-vpn/
```

### Module Interface Conventions

- `versions.tf` MUST pin provider minimum versions using `>=` with an upper bound `< N`.
- `variables.tf` MUST declare type and description for every variable; no `any` types
  unless the provider forces it.
- `outputs.tf` MUST be present even if empty; it signals the module is complete.
- Default values for optional variables MUST be the most secure, least-privileged choice
  (e.g., `private_ip_enabled = true`, not `false`).

### Naming Conventions

| Resource Type | Pattern | Example |
|---|---|---|
| VPC | `<env>-main-vpc` | `example-main-vpc` |
| Subnet | `snet-<env>-<purpose>-<visibility>` | `snet-example-gke-private` |
| GKE cluster | `<env>-gke-<purpose>` | `example-gke-private` |
| Cloud SQL | `<env>-sql-<engine>` | `example-sql-pg` |
| NAT router | `<env>-cloud-nat` | `example-cloud-nat` |
| Firewall rule | `<env>-fw-<direction>-<protocol>-<purpose>` | `example-fw-ingress-tcp-iap` |

### Commit Message Format

```
<type>(<scope>): <subject>

<body>

<footer>
```

Types: `feat`, `fix`, `refactor`, `docs`, `chore`, `security`
Scope: module path or stack name (e.g., `modules/networks/vpc`, `stacks/example`)

## Development Workflow

### Before Implementation

1. **Think before coding** (Principle VII) — State assumptions, surface ambiguity, ask
2. **Understand the requirement** — What resource, what environment, what constraints?
3. **Plan with verification** (Principle X) — Write steps with `terraform output` /
   `gcloud` checks
4. **Choose module vs. inline** — Does this resource appear in more than one stack?
5. **Get approval** — Present plan for review before significant HCL work

### During Implementation

1. **Branch from main** — Use `feat/`, `fix/`, `refactor/` branch prefixes
2. **Stay surgical** (Principle IX) — Touch only files the requirement demands
3. **Run pre-commit hooks locally** — `pre-commit run --all-files` before pushing
4. **Validate incrementally** — `terraform validate` and `terraform plan` after each
   logical change, not only at the end
5. **Commit atomically** — One commit per logical infrastructure change with a
   clear message

### Code Review Requirements

- All changes require at least one approval from a team maintainer
- Module interface changes (variable additions/removals/type changes) require explicit
  callout in PR description with migration notes
- Security-affecting changes (IAM, firewall, VPN, encryption) require security-focused
  review
- `terraform plan` output MUST be attached for any non-example stack change
- Reviewers MUST verify every changed resource traces to the stated requirement
  (Principle IX)

### Pre-Commit Gates (Automated)

These run on every commit and MUST pass before pushing:

| Hook | What It Checks |
|---|---|
| `terraform-fmt` | All `.tf` files formatted per HCL style guide |
| `tflint` | Provider-specific lint rules and best practices |
| `terraform-docs-go` | Module READMEs are up-to-date with current variables/outputs |

## Governance

### Constitution Authority

This constitution supersedes all other development practices and guidelines for this
repository. When in conflict, constitution principles take precedence over convenience,
speed, or personal preference.

### Amendment Process

1. **Proposal** — Document the change with rationale in a PR description
2. **Review** — Team review and discussion (minimum 48 hours open)
3. **Approval** — Requires consensus from all active maintainers
4. **Propagation** — Update templates and CLAUDE.md if principles change
5. **Documentation** — Increment version, update `Last Amended` date, add sync report

### Versioning Policy

- **MAJOR** (X.0.0): Principle removal, backward-incompatible redefinition, or
  fundamental workflow change
- **MINOR** (0.X.0): New principle added, new section, or significant guidance expansion
- **PATCH** (0.0.X): Clarifications, wording improvements, typo fixes, non-semantic
  refinements

### Compliance Review

- All PRs MUST verify compliance with constitution principles (checklist in PR template)
- Violations require explicit justification in the PR description
- Quarterly audits to identify drift from constitution (last reviewed: TODO)
